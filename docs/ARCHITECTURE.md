# 架构说明

## 数据边界

程序把资料根目录中的每个合法一级子目录视为一条联系单记录。原始文件是二进制
证据，JSON 通过相对路径、大小和 SHA-256 与证据关联。程序不移动、不重命名、
不覆盖既有资料；新增流程只创建新的业务目录及 DOCX/PDF。

```text
资料子目录 → 目录字段解析 ─┐
Word DOCX → 当前修订及下划线解析 ├→ 正式 JSON → HTML 汇总
其他文件 → 类型、路径、大小、哈希 ┘                ↓
                                      独立一致性校验
```

JSON 是唯一正式结构化数据源；HTML 是可随时重建的投影视图。HTML 末行的新增
表单只向本机服务提交业务输入，由服务生成文件后重新扫描并重建 JSON/HTML，页面
本身不直接编辑 JSON。文件路径一律相对于资料根目录保存，校验时必须确认解析结果
仍位于根目录内。

主题列的目录链接同样只保存相对路径。静态 HTML 直接打开时使用相对链接降级；
通过 `serve_summary.py` 访问时，页面把相对路径提交给只监听 `127.0.0.1` 的本地
服务。服务完成根目录 containment 检查后，分别调用 Windows `os.startfile`、
macOS `open` 或 Linux `xdg-open`，因此不同平台可以使用各自的 CloudStation
绝对根目录，而不改变 JSON 或 HTML。

## 分层

- 根目录入口：参数、配置、日志、退出状态。
- `flows/`：扫描、保存、新建联系单和校验的步骤编排。
- `modules/`：DOCX 解析/生成、Word PDF 导出、文件分类、哈希、原子存储、HTML、
  桌面打开和独立校验。

## DOCX 解析

解析 OOXML 的当前有效 `w:t` 文字；修订删除内容使用 `w:delText`，不会进入当前
结果。“需求内容”从“内容：”之后开始，在“备注：”之前停止，只保留带有效下划线
格式的文字，并保留段落换行。

## DOCX/PDF 新增事务

模板 DOCX 与 JSON、HTML 位于资料根目录同一层。生成器保留完整 OOXML 包及根节点
兼容性命名空间，只定点替换资料编号、日期、致送单位、事由和下划线内容段。DOCX
生成后立即回读验证；PDF 由 macOS Word AppleScript 或 Windows Word COM 导出并
检查 PDF 文件头。两者先写入资料根目录内的临时目录，全部通过后才原子改名为正式
主题目录；刷新数据库失败时会将新目录移回临时位置并清理，避免半成品。

## 增量与审计

业务身份由“专业 + 编号”生成稳定 UUID。重复扫描比较完整记录内容：新增、删除
或内容变化时增加 `dataset_revision`；每次运行保存摘要，业务变化保存逐条记录
变更。运行历史和变更历史设有上限，防止 JSON 无限增长。
